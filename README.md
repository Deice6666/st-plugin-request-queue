# 插件请求队列 (Request Queue)

给 SillyTavern 装的一道“单行道”：所有插件的生成请求排队，**上一个请求的响应体彻底读完（流式输出真正结束）之后，才轮到下一个**。
顺手解决“两个插件同时往正文里插入内容”的乱序问题 —— 因为它们再也没法同时跑。

## 它怎么判断“谁在发请求”

生成类请求最终都会打到 `/api/backends/<backend>/generate`。扩展接管 `fetch`，抢到这次请求的**调用栈**，从栈帧里认出是哪个扩展目录发起的（例如 `qr`、`JS-Slash-Runner`），认不出来的算 SillyTavern 本体（`__core__`）。

- 只拦生成接口：`/api/characters/all`、`/api/backends/<backend>/status` 这类照旧直通。
- 栈里带 `/scripts/extensions/third-party/<名字>/` 就算那个插件；内置扩展目录同理。

### 它不抢 `window.fetch` 的位置（这点很重要）

有些插件（消息预览、调试面板、破甲、工具调用、统计、重试、压缩…）会把自己的包装器盖在 `window.fetch` 上，在包装器里改请求、改响应。**这种插件必须待在它自己以为的那一层**，位置被别人换掉，它改的东西就不是它以为的那一份，功能会直接失灵。

所以本扩展只做一次被动接管：

- 加载时把 `fetch` 换成自己，往后有人再往上包，就让它包 —— 谁在上面谁先看到请求，本扩展只负责“轮到你的时候才真的发出去”。
- 往下传请求时经过原来那一层，**不跳过任何插件**，请求体、响应体照旧由它们改。
- 包装器如果绕回来又调一次 `fetch`，用内部记号保证同一个请求不会排两次队，也绝不无限递归。

### 归属怎么判断

调用栈里，越靠内越接近本扩展，越靠外越接近真正的发起者：

- **探针探测**：用一段带假插件路径的代码发一次假请求。探针自己的帧就是“发起者”，夹在它和本扩展之间的**每一层**包装器都记成转发层。之所以要全记：真正的发起者常常在 async 链里丢掉自己的栈帧，这时栈里剩下的全是包装器，只记最内层的话，次内层那个（比如 JS-Slash-Runner）就会被当成发起者，所有请求都记到它头上。
- **两次确认**：栈里推出来的转发层要连中两次才正式认账，避免某插件偶尔夹在中间一次就被永久排除。
- **三种兜底**：栈里有内置扩展帧 → 算那个内置扩展；有酒馆本体帧 → 算酒馆本体（`__core__`）；两者都没有、只剩转发层 → 算在**最外层那层壳**身上。

最后这条是给脚本运行时用的兜底：像 JS-Slash-Runner 这种“辅助插件”自己不生成内容，是它里面跑的脚本在发请求。脚本本身往往不留栈帧，所以请求算在替它发请求的那个壳上（面板里就会出现 `JS-Slash-Runner` 这一行，可以单独给它排序）。想知道到底是谁发的，打开「输出调试日志到控制台」，面板的实时状态里会摊开最近一次请求的完整调用栈。

面板里「转发层」一栏显示探针找到的结果，也可以手动填目录名（一行一个）强制排除。

### JS-Slash-Runner 里的脚本能单独认出来

JS-Slash-Runner 把每个用户脚本跑在一个**独立的同源 iframe** 里，iframe 的 `id` / `name` 就是 `TH-script--<脚本名>--<脚本id>`。本扩展利用这一点：

- 逐个桥接这类 iframe：把脚本 iframe 里的 `fetch` 接到主页面，并在请求上带一个隐藏记号（`Symbol.for('st-request-queue.origin')`），值就是脚本名。脚本自己发多少请求都不会串到别人头上，也不会漏排队。
- 另外给 `TavernHelper._bind` 上的函数套一层：脚本调用 `TavernHelper.generate(...)` 这类接口时，也能认出调用者是哪个脚本。
- 面板「请求顺序」里每个脚本各占一行，名字显示成 `脚本 · 摘要测试`，可以和插件一样拖动排序、单独取消「排队」。
- 「把 JS-Slash-Runner 里的脚本单独列出」取消勾选后，所有脚本并回 `JS-Slash-Runner` 一行。
- 只桥接 `TH-script--` 的 iframe，`TH-message--` 的消息 iframe 完全不碰。
- 新加的脚本不用刷新页面：观察到新 iframe 就当场接上；iframe 重新加载会再接一次。真遇到接不上的（脚本 iframe 藏在 shadow DOM 里、或上钩子前就把 `fetch` 存成了变量），点「重新扫描脚本」按钮手动扫一遍，比 F5 省事。

已知取舍：脚本名里如果本身含 `--`，按最后一个 `--` 切分会截错（JS-Slash-Runner 自己的 `_getScriptId` 也是这个取舍）；脚本若在桥接之前就把 `fetch` 存进了变量、或者用 XHR / WebSocket，那部分请求仍绕不过本扩展一贯的边界。

## 安装

1. 把整个 `st-plugin-request-queue` 文件夹复制到：

   ```
   SillyTavern/public/scripts/extensions/third-party/st-plugin-request-queue
   ```

   直接 git clone 最省事：

   ```bash
   cd SillyTavern/public/scripts/extensions/third-party
   git clone https://github.com/Deice6666/st-plugin-request-queue.git
   ```

   已经手动复制过的话，用这条覆盖更新（路径改成你自己的酒馆目录）：

   ```powershell
   Copy-Item -Force index.js,queue-core.js,settings.html,style.css,README.md '<你的酒馆>/public/scripts/extensions/third-party/st-plugin-request-queue'
   ```

   文件夹叫什么名字都行，模板路径和设置键会跟着真实目录名走。

2. 刷新酒馆页面（F5），打开「扩展」面板，找到 **插件请求队列 (Request Queue)**。
3. 面板里刷新列表 → 用 ↑ ↓ 调顺序 → 完事。

## 面板说明

面板用的是酒馆自身那套折叠块（和「正则」「向量存储」一样：标题一行 + 右侧圆形箭头 + 展开动画），点击标题行展开/收起。默认**收起**，只占一行；你上次的选择会记在设置里。

| 控件 | 作用 |
| --- | --- |
| 标题行 | 点击展开 / 收起面板（走酒馆原生抽屉行为）。收起时悬停能看到“现在谁在请求”。 |
| 启用请求队列 | 总开关，在面板内容最上面。关掉立刻恢复原来的并行行为（等待中的请求会被释放）。 |
| 顺序模式 | `按排序优先`：列表越靠上越先拿锁；`严格先来先到`：不看排序。 |
| SillyTavern 本身的生成也排队 | 建议开。关掉后你自己的对话楼层可以插队，但也就失去了“一次只跑一个”。 |
| 交接间隔 | 上一个请求结束后再等多久放行下一个，默认 200ms。插件来不及把结果写进正文就调到 500~1000。 |
| 单请求超时 | 卡死的请求到点强制放行，默认 10 分钟，0 表示不限。 |
| 请求顺序 | **只列你另外安装的插件**（内置扩展和本扩展自己不出现）。从上到下即优先级；取消勾选「排队」= 该插件完全放行。JS-Slash-Runner 里的脚本会各占一行，显示成 `脚本 · 脚本名`。 |
| 把 JS-Slash-Runner 里的脚本单独列出 | 默认开。开着就按脚本单独排队排序；关掉则所有脚本并回 `JS-Slash-Runner` 一行。后面的灰字是已经发现的脚本，右边的「重新扫描脚本」按钮可以手动重扫一遍。 |
| 只显示发过请求的 | 默认开。面板只列真的发过生成请求的插件/脚本（字体、主题、按钮、美化这类纯界面扩展不占位置）。取消勾选可看全量名单，方便提前排序；「清空记录」把“发过请求”的记录清零。 |
| 附加规则 | 额外要排队的接口，每行一条，支持 `/正则/`。 |
| 转发层 | 手动指定“只转发别人请求”的插件目录名（一行一个），会自动探测并填在上面提示。 |
| 实时状态 | 谁在跑、跑了多久、谁在排队、最近几次耗时。 |

调度上的两个隐式规则：

- SillyTavern 本体（你自己发的对话）**恒为最高优先级**，插件之间的先后才按列表来。
- 等太久（默认 45 秒）的请求会被临时提权，避免某个插件永远排不上。

斜线命令：`/rq` 看状态、`/rq-on`、`/rq-off`、`/rq-flush` 清空队列。

## 给插件作者用（可选）

不想等 fetch 层猜归属，可以在自己的插件里显式占位：

```js
const release = await globalThis.STRequestQueue?.acquire?.('我的插件');
try {
    // ……发请求、把结果写进正文……
} finally {
    release?.('done');
}
```

或者用更省事的包装（整个异步任务期间独占）：

```js
await globalThis.STRequestQueue?.run?.('我的插件', async () => {
    const res = await fetch('/api/backends/chat-completions/generate', { /* ... */ });
    await res.text();
});
```

## 边界（别指望它做不到的事）

- **只管 `fetch`**。插件用 `XMLHttpRequest`、WebSocket 直连第三方 API、或者在自己进程里跑推理，它拦不到。
- 归属靠调用栈。插件如果先把 `fetch` 存进变量、再从一个无名闭包里调用，可能被认成本体 —— 这种就把它填进「转发层」。
- JS-Slash-Runner 的脚本靠 iframe 桥接认身份：桥接那一刻之前就被脚本存进变量的 `fetch`、脚本自己发的 XHR / WebSocket 都认不出来（那些请求本身也照样不排队）。
- 有插件把 `fetch` 整个换成自己的实现、又不往下传时，请求根本到不了本扩展；这种情况本扩展管不到（面板会显示「暂无请求」）。
- 直连 OpenAI / Claude 官方域名（不走酒馆后端）的请求不在拦截范围；真需要就把域名片段加进「附加规则」。
- 队列是**页面内**的。开了多个酒馆标签页，各排各的。
- 不改变模型输出质量，也不解决“插件本身写正文逻辑有 bug”。

## 排查

面板里勾上「输出调试日志到控制台」，F12 控制台会打印 `[请求队列] enqueue / grant / release` 全过程：

- 根本没有 `enqueue` → 请求没走 `fetch`，或接口不在匹配范围（加附加规则）。
- 一直 `grant` 同一个 key、后面没动静 → 把「交接间隔」调大，或看是不是取消了那个插件的「排队」勾。
